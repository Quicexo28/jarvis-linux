# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Run commands

Independent services — separate terminals (or via systemd in production).

- **Backend** (Node ESM): `cd backend && npm run dev` — boots on `http://0.0.0.0:8788`. Tests: `npm test`.
- **Frontend** (Vite dev): `cd frontend && npm run dev` — port 5173. Build: `npm run build`. Tests: `npm test`.
- **Tauri dev** (desktop shell + frontend): `cd frontend && npm run tauri` — launches Tauri window, registers Super+J global shortcut.
- **Tauri production build**: `cd frontend && npm run tauri:build --no-bundle` — output in `frontend/src-tauri/target/release/jarvis`.
- **STT service** (Python, CPU): `cd backend/voice/python && .venv/bin/python stt_service.py` — faster-whisper + Silero VAD on port `8790`.
- **TTS service** (Python, GPU): `cd backend/voice/python && .venv/bin/python xtts_service.py`.
- **Wake word service**: `cd backend/voice/python && .venv/bin/python wake_service.py` — openWakeWord, signals backend.
- **Python deps**: `cd backend/voice/python && .venv/bin/pip install -r requirements.txt`.
- **MCP server deps** (first-time): `cd backend/mcp-server && npm install`.

Root-level shortcuts: `npm run dev:backend`, `npm run dev:frontend`, `npm run build:frontend`, `npm run test:backend`, `npm run test:frontend`.

### Production (systemd)

Services live in `scripts/linux/*.service`, installed to `~/.config/systemd/user/` by `scripts/linux/install.sh`. Assumes repo at `~/jarvis-linux/` — systemd `%h` expands to `$HOME`.

```
systemctl --user start jarvis-backend jarvis-stt jarvis-tts jarvis-wake jarvis-ui
systemctl --user start jarvis-jarvisbot jarvis-cloudbot jarvis-notifier   # after secrets set
journalctl --user -u jarvis-backend -f
```

`jarvis-ui.service` runs the **Tauri binary** (`frontend/src-tauri/target/release/jarvis`), which embeds the frontend at build time — **always `npm run tauri:build --no-bundle` BEFORE restarting `jarvis-ui`**, or the restarted process serves stale assets (symptom: skill-bus primitives fail with errors from old code, e.g. `invalid_model3d_kind`). For Chromium app-mode instead, point `ExecStart` at `chromium --app=http://localhost:8788`.

### Relaunching after updates

**Always restart affected services after applying changes.** Rules by change type:

| Changed | Services to restart |
|---------|-------------------|
| `backend/src/**` (any JS) | `jarvis-backend` |
| `backend/voice/python/*.py` | `jarvis-stt` and/or `jarvis-tts` / `jarvis-wake` (whichever was changed) |
| `backend/voice/python/requirements.txt` | Re-run `pip install -r requirements.txt` inside `.venv`, then restart affected Python service |
| `backend/package.json` / `package-lock.json` | `npm install` in `backend/`, then restart `jarvis-backend` |
| `frontend/src/**` (Tauri — current `jarvis-ui.service`) | `npm run tauri:build --no-bundle`, **then** restart `jarvis-ui` (build first: assets are embedded in the binary) |
| `frontend/src/**` (Chromium app-mode alternative) | `npm run build` in `frontend/`, then restart `jarvis-ui` |
| `scripts/linux/*.service` | `systemctl --user daemon-reload`, then restart changed service |
| `.mcp.json` or `backend/mcp-server/**` | Reload Claude Code MCP connection (no systemd unit) |
| `backend/data/secrets.local.json` | Restart `jarvis-backend` (secrets loaded at boot) |

Quick restart commands:

```bash
# Backend only
systemctl --user restart jarvis-backend

# All core services
systemctl --user restart jarvis-backend jarvis-stt jarvis-tts jarvis-wake jarvis-ui

# After .service file change
systemctl --user daemon-reload && systemctl --user restart <service-name>

# Check status / logs after restart
systemctl --user status jarvis-backend
journalctl --user -u jarvis-backend -f
```

**Dev mode exception:** Frontend changes hot-reload automatically when `npm run dev` is active — no restart needed. Backend changes with `npm run dev` (nodemon) also auto-reload.

### Hyprland integration

Source `scripts/linux/hyprland-jarvis.conf` from `~/.config/hypr/hyprland.conf` to apply window rules (no border, no animation, always-on-top pin) for the Chromium app window (class `chromium`, title `Jarvis`).

## Architecture

### Desktop shell: Tauri vs Chromium app-mode

Two deployment modes exist:

1. **Tauri** (`frontend/src-tauri/`) — Rust shell wrapping the Vite frontend. Registers **Super+J** as a global shortcut via `tauri_plugin_global_shortcut`, emitting a `jarvis:wake` Tauri event that `App.tsx` listens to with `listen('jarvis:wake', ...)`. Window is fullscreen, decorations off, transparent. The Tauri binary is self-contained; no backend process management.

2. **Chromium app-mode** — backend serves the built frontend as static files (`handlers/static.js`). `jarvis-ui.service` runs Chromium against `http://localhost:8788`. Super+J requires a separate trigger (Hyprland keybinding → backend API, or `jarvis-wake.service`).

### Boot state machine (frontend)

`bootStore.ts` owns a zustand store: `DORMANT | AWAKE | PIP`. No Electron IPC — state lives entirely in the browser. Transitions:

- **Super+J** → Tauri emits `jarvis:wake` → `App.tsx` calls `setBootState('AWAKE')`.
- **Double clap** → `useClapDetection` (adaptador WebAudio) + `audio/clapEngine.ts` (DSP puro, testeable en Node) fires `setBootState('AWAKE')`. Gates por frame: LOUD (sobre suelo adaptativo **y** piso absoluto `absMinRms`), SHARP (ataque), BROADBAND (planitud > 0.9), NO-GRAVE (<1 kHz aporta < 40%). Gates de par: el primer aplauso debe CAER al 25% de su pico en ≤200 ms (validado durante la espera → gratis) y ambos espectros deben parecerse (coseno ≥ 0.80). Dos onsets 200–1000 ms aparte = doble aplauso; dispara en el SEGUNDO onset. Silenciado mientras `isTtsSpeaking()`. Micro compartido vía `micFeed` (`noiseSuppression:false` + `autoGainControl:false`). `debug: true` loguea cada evento; el disparo se loguea SIEMPRE (`[clap] DOBLE APLAUSO ...` → journald).
- **Sleep tool** → backend `POST /api/skills/system/sleep` → skill bus → frontend calls `setBootState('DORMANT')`.

`DormantLayer` always mounts and runs clap detection while `DORMANT`. `AwakeApp.tsx` mounts when `AWAKE`.

### Backend (`backend/src/`)

`server.js` — thin `http.createServer`. Static frontend served before API dispatch (`handlers/static.js`). WebSocket upgrades dispatched by path in a single `upgrade` listener.

**Handlers** (`handlers/`): `health`, `modules`, `telemetry`, `jarvis` (TTS/turn/tts-WS), `stt` (HTTP upload + WS proxy to Python), `speech` (intent gate → Claude CLI), `speakerId` (voice sample CRUD), `mobile` (QR token auth), `mobileGesture` (WS for phone gestures), `skillTools` (all `/api/skills/*` endpoints), `uiState`, `pcControl`, `obsidian`, `security`, `config`, `wakeWord`, `selfBuild`.

**Libs** (`lib/`):
- `skillBus.js` — duplex WS channel (`/api/skills/bus`) from Node backend → AWAKE renderer. `requestClient(verb, payload)` sends a primitive request and awaits correlated response. Falls back to `nativePrimitives.js` if no renderer connected.
- `attentionState.js` + `intentClassifier.js` — speech intent gate. States: `ENGAGED` (0–15 s), `ATTENTIVE` (15–60 s), `PASSIVE` (>60 s). Speaker confidence ≥ 0.65 required.
- `conversationMemory.js` — sliding 8-turn window, in-process global (resets on restart).
- `claudeCli.js` — spawns `claude --print --model ...` with conversation context.
- `secrets.js` — loads **`backend/data/secrets.local.json`** (gitignored) into `process.env` at boot. **La ruta es `data/`, no la raíz de `backend/`** — un `backend/secrets.local.json` se ignora en silencio y parece que la clave «no se cargó». Env existente GANA sobre el fichero, así que una variable ya puesta en el `.service` no se puede sobrescribir desde aquí.
- `linuxKeyring.js` — Linux equivalent of Windows DPAPI. Uses `secret-tool` (libsecret) for machine-scoped AES-256-GCM key; falls back to `~/.config/jarvis/machine.key` (chmod 600) on headless.
- `obsidian.js` — reads/writes vault via filesystem. `portableVault.js` for encrypted portable storage.
- `telegramBot.js`, `reminders.js`, `cloudflareTunnel.js`, `pdfWatcher.js` — background services started at boot.
- `tailscale.js` — Tailscale URL for mobile QR pairing outside LAN.

**Agent system** (`agent/`):
- `bridge.js` — WS at `/api/jarvis/agent/ws`. Duplex link between frontend capability registry and the backend brain. Protocol: frontend sends `hello` (tools + snapshot), then `turn` (user utterance) or `tool_result`; backend replies with `tool_call` or `final` (spoken reply).
- `brain.js` — the AI decision layer, called by the bridge.

**Services** (`services/`): `jarvisBot.js` (Telegram voice bot), `cloudBot.js`, `notifier.js`.

**MCP server** (`backend/mcp-server/`): Separate Node ESM package. Exposes all Jarvis skills (timer, chrono, reminder, navigation, Obsidian, display, 3D, cloud) as MCP tools over stdio. Claude Code connects to it via `.mcp.json`. Run `npm install` inside this directory if `node_modules/` is missing.

### Distributed agents (`agents/` Cargo workspace)

Jarvis actúa sobre otras máquinas (Windows "main" primero) vía agentes ligeros headless. Cerebro = backend Node (no Rust); el Rust vive en un workspace **separado** `agents/` (crates `protocol`, `hub`, `agent`).

- **`protocol`** — tipos serde compartidos hub↔agente + `PROTOCOL_VERSION` (chequeado en handshake). `RemotePath` tipa Win/Linux (nunca parte por separador). `cargo run -p jarvis-agent-protocol --bin gen-schema -- backend/data/agents` emite `protocol.schema.json` + versión para el lado Node (fuente de verdad única).
- **`hub`** — sidecar Rust en el portátil. WS server `0.0.0.0:8794` (agentes conectan INBOUND por Tailscale, no exponen puerto; token por-agente en handshake). Control API `127.0.0.1:8795` para el backend Node (`/machines`, `/rpc`). Eventos proactivos → POST a Node `/api/agents/event` → `notifyJarvis` (Telegram). systemd: `jarvis-agenthub.service`. **Puertos 8794/8795** (8789-8791 son python; 8792 pc_control).
- **`agent`** — binario headless. WS-client, handshake (versión+token+MACs para WoL), heartbeat, reconexión backoff (portátil suspende), multiplexado (ops en `spawn_blocking`). Allowlist local (exec/write OFF por defecto — el agente veta aunque el hub pida) + audit log. Windows Service tras `--features winservice` (módulo `winservice.rs`, **sin validar en Linux** — Fase 6, lo prueba el Claude de Windows). Linux/systemd = mismo binario.
- **Node seam**: `handlers/agents.js` (`/api/agents/list|rpc|control|wake|event`), tokens en `backend/data/agent-tokens.json` (revocables). `/api/agents/rpc` es **local-only** (webAuth DANGEROUS — puede disparar exec remoto); `/api/agents/control` es la puerta REMOTA (token web) con allowlist de ops server-side: `sys_info`/`list_processes`/`search`/`wake` siempre, y `exec`/`read_file`/`write_file` solo con `JARVIS_AGENTS_REMOTE_EXEC=1`. `/api/agents/list` fusiona TRES fuentes: **el propio portátil** (`local:true`, primero — hospeda el hub, así que nunca aparece como agente y sin esto el PC que ejecuta Jarvis era el único ausente de la lista), las máquinas conectadas del hub, y las conocidas de `agent-tokens.json` (`online:false`, para encenderlas por WoL). Al portátil le responde `lib/localAgent.js` en Node (`sys_info`/`list_processes`/`search` con la MISMA forma `OpResult` del protocolo, así el cliente no distingue local de remoto); `exec`/`read_file`/`write_file` NO están ahí a propósito — para eso ya existen las rutas de sistema/`code/*`, todas local-only. `servedLocally()` consulta el hub antes de responder en local, para que un agente real con el mismo hostname gane siempre. MCP tools `remote_machines/remote_sysinfo/remote_search/remote_exec` en `jarvis-mcp.js` (usan `transform` para envolver en el envelope RPC del hub).
- **Estado v1**: Fases 1-5 completas y verificadas en Linux; agente Windows `main` en producción. Fase 1-2 = protocol + hub + agent (handshake/reconnect/heartbeat/allowlist/audit). **Fase 3** (`ops.rs`) = search (Everything `es.exe` Windows-only + fallback walkdir), exec (buffered, timeout con kill, pipes drenados en hilos, `from_utf8_lossy` consola OEM), read/write file (base64, chunked offset/length, cap 4 MiB), list_processes (sysinfo top-50 mem). **Fase 4** = MCP tools `remote_machines/sysinfo/search/exec/read_file/write_file/wake` (`jarvis-mcp.js`; `remote_read_file` decodifica base64→text por `postTransform`). **Fase 5** (`watch.rs`) = watchers proactivos: `Booted` (una vez), `DiskHigh` (edge-triggered por montaje sobre `disk_percent`), `ProcessExited` (procesos vigilados en `[watchers]` de agent.toml) → Event → hub → `/api/agents/event` → Telegram. **Wake-on-LAN**: hub cachea MACs por handshake en `agent-macs.json` (gitignored), `/wake` + `/api/agents/wake` + `remote_wake` mandan magic packet UDP broadcast (SOLO misma LAN — no viaja por Tailscale). **El hub caduca agentes mudos** (`AGENT_SILENCE_TIMEOUT`, 60 s = 3 pings perdidos): un apagón deja el TCP medio abierto (sin FIN ni RST) y sin plazo el lector se bloquea hasta que el keepalive del kernel se rinde (~2 h), así que `/machines` seguía reportando la máquina CONECTADA — y la app, que solo ofrece «Encender» a las offline, nunca mostraba el botón. Cualquier trama entrante reinicia el plazo. **El hub emite a TODAS las broadcast**: la limitada `255.255.255.255` sale por UNA sola interfaz (la de la ruta por defecto) y hay APs que no la cruzan de Wi-Fi a cable, así que también manda la dirigida de cada IPv4 local (`192.168.1.255`…) vía `if-addrs`, saltando loopback y /32 (tailscale0). La respuesta trae `sent` (MACs alcanzadas) y `packets` (datagramas). Estado en `main` verificado 2026-08-08: `Wake on Magic Packet=Enabled`, `Shutdown Wake-On-Lan=Enabled`, `HiberbootEnabled=0`. **Ojo al depurar**: un listener UDP en el Windows encendido NO recibe nada (el firewall descarta hasta el unicast), y eso NO dice nada sobre el WoL real — con la máquina apagada el paquete lo procesa la NIC en hardware, antes de que exista firewall. **Bug corregido**: `Event.kind` colisionaba con el tag `"kind"` del enum `Message` → renombrado a `"event"` en el wire (`#[serde(rename)]`); test de regresión en protocol. **CPU de `sys_info` es un DELTA**: sysinfo necesita DOS muestras separadas por `MINIMUM_CPU_UPDATE_INTERVAL`; con `System::new_all()` + un solo `refresh_all()` reportaba basura (78% con la máquina ociosa). Arreglado en `ops.rs` (sleep + `refresh_cpu_usage()`, igual que ya hacía `list_processes`) y **desplegado en `main` el 2026-08-08** (antes: 78% con Windows midiendo 15%; después: 9.9% contra 7%). **Receta de despliegue sin matar el canal**: compilar EN main por ruta completa del toolchain MSVC (`C:\Users\santi\.rustup\toolchains\stable-x86_64-pc-windows-msvc\bin\cargo.exe`, con `CARGO_HOME`/`PATH` puestos línea a línea desde un `.cmd` — `set VAR=val && cmd` deja un espacio en el valor y cargo falla con "failed to acquire package cache lock"); luego `move` del exe EN USO (Windows lo permite) + `copy` del nuevo + `sc failure JarvisAgent reset= 86400 actions= restart/5000` + `taskkill /f` → el SCM revive el servicio con el binario nuevo. `start`/`schtasks` desacoplados NO funcionaron (el primero no ejecutó nada; el segundo lo bloquea el clasificador). Rollback: `C:\Progra~1\Jarvis\jarvis-agent.old.exe`. **Pendiente**: Fase 6 = Windows service nativo (winservice.rs — `main` ya corre como servicio SYSTEM, validado en la práctica); streaming real de exec (hoy buffered); auto-update v1.5 (`Welcome.expected_agent_version` listo, swap sin implementar). Hub = `jarvis-agenthub.service` (0.0.0.0:8794, ufw tailscale0).

### Autodesarrollo (Jarvis modifica su propio código)

Pedirle por voz "arregla X en tu código" lanza un **agente Claude Code completo** sobre el repo. El cerebro de voz (haiku, ~30 s de turno) NO edita: **delega**.

- **`lib/devAgent.js`** — runner de jobs. `startDevJob({instruction})` → (1) `gitCheckpoint` (punto de restauración), (2) `spawn claude --print --output-format stream-json --dangerously-skip-permissions --model sonnet --append-system-prompt <reglas>` con `cwd` = raíz del repo (el agente lee este CLAUDE.md solo), (3) `git diff` contra el checkpoint, (4) **aplica**: `planApply()` mapea archivos→acciones según la tabla "Relaunching after updates" (python→`systemctl restart jarvis-stt/tts/wake`, frontend→`tauri:build --no-bundle` + restart `jarvis-ui`, backend→restart, `.service`→`daemon-reload`), (5) avisa por Telegram (`notifyJarvis`) + toast del renderer. **Asíncrono**: el turno de voz solo acusa recibo; el resultado llega minutos después.
- **Un job a la vez** (`active`). Jobs persistidos en `backend/data/dev-jobs/<id>.json` + `.log` ANTES del restart, porque el propio backend se reinicia al final y la memoria se pierde.
- **El restart del backend va SIEMPRE al final y por `scheduleRestart()` (exit 99 + `Restart=on-failure`)**, nunca `systemctl --user restart jarvis-backend`: el agente y el runner viven en el cgroup del backend y un systemctl los mataría a mitad. Por lo mismo el prompt del agente le PROHÍBE reiniciar backend/UI y ejecutar el build de Tauri — de eso se encarga `applyChanges` cuando ya terminó.
- **El agente termina con `RESUMEN: <frase>`** — es lo único que se lee en voz alta (`extractSummary`, con fallback a la última línea).
- **Rutas** `/api/skills/code/task|task/status|task/cancel` (+ las previas `run|checkpoint|rollback|restart`), todas POST. Triple barrera: local-only (webAuth `DANGEROUS_PATHS` cubre `/api/skills/code/`), `ownerOnly` (speaker OWNER) y `requireCodeAuth`. **Tools MCP**: `code_task`, `code_task_status`, `code_run`, `code_checkpoint`, `code_rollback`, `code_restart`.
- **Dos caminos de entrada**, a propósito: intent `self_code` en `intentClassifier.js` (verbo mutador cerca de "tu/su/el código|backend|frontend") dispara `startDevJob` directo desde `speech.js` — no depende de que haiku elija la tool; y la tool `code_task` cubre todo lo que el regex no vea. `self_code` NO está en `LIMITED_INTENTS`, así que solo el OWNER pasa el gate de `filterIntentsByMode`.
- **Env** (`jarvis-backend.service`): `JARVIS_CODE_DIR=%h/jarvis-linux` — **sin esto Jarvis no ve su propio código** (`getCodeDir()` alimenta el prompt de autodesarrollo Y las roots del MCP filesystem); `JARVIS_CODE_TRUST_LOCAL=1` autoriza sin contraseña (si hay `JARVIS_CODE_PASSWORD_HASH` la contraseña SIEMPRE manda — `node scripts/set-code-password.js`); `JARVIS_DEV_MODEL` (sonnet), `JARVIS_DEV_JOB_TIMEOUT_MS` (25 min), `JARVIS_DEV_BUILD_TIMEOUT_MS` (15 min).
- **Ojo con el checkpoint**: `gitCheckpoint` hace `git add -A` + commit en la rama actual, así que el primer job **compromete todo el árbol sucio** en un commit `jarvis-checkpoint:`. Es lo que hace que `code_rollback` (reset --hard) sea seguro; si no lo quieres, commitea tú antes.

### Memoria persistente y telemetría de turnos

Jarvis recuerda entre reinicios y cada turno queda medido. Tres piezas nuevas: `lib/turnStore.js` (SQLite), `lib/memory.js` (recall + aprendizaje) y `scripts/eval-voice.mjs` (arnés). Antes de esto la memoria eran 8 turnos en RAM (`conversationMemory.js`, muere al reiniciar), el historial del vault se escribía sin que nadie lo leyera, y la única traza era una línea `[turn]` en journald.

- **`turnStore.js` usa `node:sqlite`, que es BUILT-IN** (Node 22+; aquí 26.3) — cero dependencias nuevas. DB en `backend/data/jarvis.db` (gitignored). Tablas `turns` (transcripción, intent, modelo, tools llamadas, latencias, tokens, coste, session_id, error), `facts` (memoria a largo plazo) y `kv`. Búsqueda por **FTS5 con `remove_diacritics 2`**, que es lo que hace que "cafe" encuentre "café". **`node:sqlite` se carga con `createRequire`, NO con import estático**: el vite que trae vitest resuelve contra su propia lista (vieja) de builtins y un import estático mata la suite entera en la fase de colección con `Failed to load url sqlite`.
- **Recall antes del turno, aprendizaje después.** `recallContext(text)` busca hechos por FTS5 (sub-ms, local) y los inyecta en `extraContext` junto a la fecha; `learnFromTurn()` lanza un haiku barato que extrae hechos DURADEROS del intercambio y los guarda — **fire-and-forget, jamás en el camino de la voz** (misma disciplina que `_learn_async` del STT). Es BM25, no embeddings, a propósito: ya está instalado, no carga modelo ni GPU. Embeddings son la ruta de mejora cuando las trazas muestren fallos de recall, no el punto de partida. Env: `JARVIS_MEMORY_RECALL|LEARN|FACTS|TURNS`.
- **`runClaude` devuelve SOLO LA ÚLTIMA LÍNEA de stdout** — comportamiento histórico para descartar ruido del CLI antes de una respuesta de una línea. Un extractor que responde un array JSON multi-línea llegaba como `]` y la memoria aprendía cero, en silencio. De ahí la opción `multiline: true`; cualquier caller nuevo cuya respuesta ocupe varias líneas la necesita.
- **Las sesiones sobreviven al reinicio del backend** (`claudeCli.js`): cada `ClaudeSession` fija un UUID estable, lo persiste en `kv` y usa `--session-id` la primera vez y **`--resume` después**. La distinción importa: el id restaurado ya tiene transcript en disco, así que re-reclamarlo con `--session-id` falla — sobrevivía al crash del CLI pero NO al `systemctl restart`. Verificado en vivo: palabra dicha antes del reinicio, recordada después. `--autocompact auto` acota el transcript de una sesión que vive días. Apagar con `JARVIS_SESSION_RESUME=0`. **`--bare` NO sirve aquí**: fuerza `ANTHROPIC_API_KEY` y rompe la auth por suscripción.
- **El `stderr` de la sesión se descartaba entero** (`proc.stderr.on('data', () => {})`), así que un proceso que moría no dejaba explicación en ningún sitio: el único síntoma era Jarvis perdiendo la conversación. Ahora se guarda la cola y se registra al salir.
- **El evento `result` del CLI trae mucho más que el texto**: `session_id`, `usage` (con tokens de caché), `total_cost_usd`, `duration_ms`, `ttft_ms`, `is_error`. Todo eso se tiraba. También se capturan los `tool_use` del stream y los `tool_result` con `is_error` — **antes era imposible distinguir "lo hizo" de "dijo que lo hizo"** sin mirar la pantalla. Se leen por `GET /api/jarvis/stats?hours=24` (volumen, p50/p90, coste, mezcla de modelos e intents) y `GET /api/jarvis/memory` (+ `POST /api/jarvis/memory/forget` con `{id}`: una memoria que nadie puede corregir no sirve).
- **`npm run eval:voice`** reproduce `tests/fixtures/voice-cases.json` contra el backend VIVO y verifica lo que de verdad pasó — qué tools corrieron, si alguna falló, cuánto tardó la primera frase — leyendo la fila de `turns`. **Gasta tokens de verdad y maneja el asistente real** (arranca timers, abre vistas). Y **exige la UI DESPIERTA**: reiniciar `jarvis-backend` deja la UI en DORMANT (`Requires=`), y entonces todo lo que toque el renderer falla con `renderer_not_connected` — se despierta con `POST /api/skills/system/wake` antes de medir. Baseline con UI despierta: 5/5.

### Verificación de turnos (¿de verdad pasó?)

`lib/verifier.js` comprueba, DESPUÉS de que la respuesta salió a TTS (coste cero en latencia), que lo dicho coincide con lo que ocurrió. Generaliza el antiguo `enforceDisplayClaim` de `speech.js`, que cubría un solo síntoma (enlaces dichos en voz sin tarjeta). Cuatro chequeos, en este orden, y **como mucho UN correctivo por turno** (Jarvis no puede hablar encima de sí mismo). El veredicto se guarda en la columna `verdict` de `turns` y sale agregado en `/api/jarvis/stats` (`byVerdict`). Kill switch `JARVIS_VERIFY=0`; el de display sigue siendo `JARVIS_ENFORCE_DISPLAY=0`.

- **A. Honestidad ante el fallo** — si alguna tool devolvió `is_error`, ¿la respuesta lo admite (`tool_error_reported`) o lo tapó (`false_success`)? Este es el peor modo de fallo de un asistente de voz y era invisible: la palabra del modelo era la única evidencia que producía un turno.
- **B. Postcondiciones** — para tools que "salieron bien", se consulta el estado REAL por el skill bus: `open_view` → `view_current` coincide, `timer_start`/`chrono_start` → la lista tiene algo, `timer_cancel(all)` → la lista quedó vacía, `show_display` → llegó al backend. **Devolver `null` significa "no comprobable" y NUNCA es fallo** (renderer caído, sin input): un turno inverificable no puede reportarse como mentira. `requestClient` devuelve el objeto INTERIOR (`{timers:[]}`, `{mode:'plan3d'}`), no el `{ok,result}` de la ruta HTTP.
- **C. Reglas de display** — las de siempre, movidas tal cual. **Van ANTES del chequeo D**: una respuesta que nombra una herramienta también parece una afirmación de acción, y con el orden inverso el chequeo genérico tapaba al específico (visto en vivo: la recomendación de navegador se clasificó `unbacked_claim` en vez de `display_missing`).
- **D. Afirmación sin respaldo** — la respuesta dice que hizo algo y no se llamó ninguna tool.

Lo que NO es obvio:

- **Una tool que falla y el modelo REMONTA no es una mentira.** Visto en vivo: `Bash` fue rechazada (está deshabilitada para la sesión), el modelo cayó a `run_terminal`, obtuvo la respuesta y la contó bien — y la primera versión lo calificó `false_success`. Disparar el correctivo ahí le diría al señor que algo falló cuando no falló, que es peor que el fallo que evita. `recovered()` mira la ÚLTIMA llamada del turno: si la acción final salió bien, la respuesta se apoya en ese éxito. Veredicto propio `tool_error_recovered` para que siga siendo visible en las estadísticas.
- **El texto de un turno correctivo SE DESCARTA — nadie lo pronuncia.** No existe primitiva `speak` en `frontend/src/skills/primitives.ts`, así que el backend no puede hacer hablar al renderer. Por eso los correctivos NUNCA se redactan como "dile la verdad al señor" (esa frase se perdería): ordenan una ACCIÓN con efecto real — reintentar la tool, o `show_display` con el mensaje. Verificado en vivo: `[verify] tool without UI action` → `[tool] display_show -> ok`. Una primitiva `speak` es la mejora natural, y es trabajo de frontend.
- **Los clasificadores corren sobre texto SIN TILDES en minúsculas** (`normalizeReply`). Misma trampa que las wake phrases: `\b` solo entiende ASCII, así que sobre "Falló al guardar" no hay frontera tras la "ó" y `/\bfall[óo]\b/` no casaba — la respuesta HONESTA se habría calificado de mentira.
- **Los participios pasados son también adjetivos.** "Firefox es de código **abierto**" disparó `unbacked_claim` en la primera versión. Ahora los participios solo cuentan en respuestas cortas (≤60 caracteres, o sea confirmaciones secas); los verbos en primera persona ("abrí", "apagué") valen a cualquier longitud. Casos reales de journald en `tests/verifier.unit.test.js`.
- **La verificación se dispara desde el WRAPPER, no desde el pipeline interno**: necesita `ctx.turnId`, que solo existe después de `recordTurn`. Lanzarla desde dentro competía con la asignación del id y el veredicto se perdía.
- El arnés `npm run eval:voice` espera al veredicto antes de aserciar, exige `verdict: "ok"` en los casos con tool, y **falla SIEMPRE ante `false_success` o `unbacked_claim`**, se hayan declarado o no.

### Permisos por riesgo, proactividad y sentidos

Tres capas nuevas sobre el cerebro de voz: `lib/toolRisk.js` (quién puede hacer qué), `lib/proactive.js` (hablar sin que le pregunten) y `handlers/vision.js` (ver). Más un agujero de seguridad cerrado en `claudeCli.js`.

- **AGUJERO CERRADO: la sesión de voz tenía `Bash` nativo.** El CLI trae Bash/Write/Edit de serie y Jarvis arranca con `--dangerously-skip-permissions`, así que un turno de voz podía ejecutar shell arbitrario como el usuario. **Verificado en vivo**: «usa tu herramienta Bash y ejecuta id» devolvió el uid real. Ese camino **esquiva por completo** el gate de riesgo, que solo ve peticiones HTTP del servidor MCP — o sea `run_terminal` estaba clasificado como destructivo mientras `Bash` estaba abierto de par en par al lado. Fix: `--disallowedTools Bash,Write,Edit,NotebookEdit,Task,KillShell,BashOutput` en la sesión persistente (`JARVIS_VOICE_DISALLOWED_TOOLS` lo sobreescribe). Se quedan WebSearch/WebFetch (capacidad real) y el MCP de filesystem (acotado a vault+código y SÍ gateado). `Task` fuera también: un turno de voz lanzando subagentes es un multiplicador de coste sin techo. **El autodesarrollo no se ve afectado** — `devAgent` lanza su propio proceso CLI. Tras el fix el modelo cae solo a `run_terminal`, que sí pasa por el gate.
- **`toolRisk.js` clasifica RUTAS, no intents.** El modelo anterior (`LIMITED_INTENTS`) se comprobaba UNA vez antes del turno; pasado ese gate el modelo podía llamar cualquiera de las ~70 tools, así que un turno clasificado «chat» podía acabar en `code_task` o `system_power`. Ahora cada ruta es `read` (mirar: listas, estados), `write` (recuperable: timers, vistas, notas, luces) o `destructive` (código propio, power, agentes remotos, inyección de input en el PC, unlock). Política: OWNER todo; KNOWN escribe pero no destruye; UNKNOWN/LOW_CONF solo mira. Lo destructivo exige además una coincidencia de voz **RECIENTE** (`JARVIS_RISK_OWNER_FRESH_MS`, 15 min): el modo de hablante es pegajoso entre turnos y sin esto una identificación de la mañana autorizaba un apagado por la tarde. Kill switch `JARVIS_RISK_GATE=0`.
  **Solo se gatea lo marcado `X-Jarvis-Origin: model`** (cabecera que pone `jarvis-mcp.js` en cada llamada). La GUI, la app del móvil y la tablet pegan a LAS MISMAS rutas, y el modo de hablante describe a quien habló POR ÚLTIMA VEZ — aplicarlo al tráfico de la interfaz bloquearía los clics del propio usuario por un turno de voz ajeno. Una ruta sin clasificar cae en `write`, que falla del lado seguro.
  **`/api/skills/vision/*` NO está en la lista de lecturas a propósito**: no cambia nada, pero una captura se lleva lo que haya en pantalla (contraseñas, mensajes), así que una voz desconocida no puede pedirle a Jarvis que mire.
- **Ojos** (`handlers/vision.js` + tools `look_screen`/`look_camera`). `grim` captura, ImageMagick reescala a 1568 px y **reencoda a JPEG q85**: medido en este panel, el PNG reescalado pesa 691 KB y el JPEG 142 KB — 5× menos por el stdio del MCP, con el texto de pantalla igual de legible. **`grim` sin `-o` compone TODAS las salidas**: aquí apilaba el portátil sobre `projmap` (la salida headless del proyector), así que la mitad de la imagen era una pared que nadie mira, el aspecto salía deformado y el modelo respondía sobre la mitad equivocada. Por eso el destino por defecto se resuelve con `hyprctl monitors -j` → el monitor **enfocado**, saltando `projmap`. La tool MCP devuelve un bloque `image`, no texto: un base64 dentro de un bloque de texto es un muro de caracteres que el modelo no puede mirar. Verificado: leyó la hora real del reloj de la barra. `look_camera` reusa la primitiva `capture_photo` del renderer (el `<video>` oculto del pipeline de gestos), así no abre un segundo stream — que es justo lo que revienta el cliente PipeWire de WebKitGTK.
  **El verificador salta el chequeo de display cuando el turno MIRÓ**: `DISPLAY_CLAIM_RE` dispara con un simple «pantalla», que antes delataba una tarjeta prometida y no mostrada. Ahora «tu pantalla está limpia» es la descripción de una observación real, y sin la excepción el correctivo saltaría en CADA respuesta de visión.
- **Primitiva `speak_text`** (`frontend/src/skills/speakBridge.ts` + `primitives.ts`, ruta `/api/skills/speech/say`, tool `speak`). Es lo que permite al BACKEND hablar por iniciativa propia. **AwakeApp registra su propio `speak()`** en el bridge en vez de que la primitiva monte su propia reproducción: ese `speak()` aborta lo que se esté diciendo y **alimenta el gate anti-eco del STT**; un segundo camino de audio haría que Jarvis se oyera a sí mismo y se contestara. Sin renderer montado no hay nada registrado y la primitiva falla a propósito — el backend tiene que enterarse de que sus palabras no salieron.
- **`proactive.js` decide si vale la pena interrumpir.** Ciclo: señales locales baratas → reglas gratis → haiku decide UNA cosa → voz si el renderer está despierto, Telegram si no. **El presupuesto se aplica en CÓDIGO, nunca se le deja al modelo**: máximo por día, horas de silencio (23→07), separación mínima entre avisos, y nada de repetir (los avisos se guardan como hechos `kind:proactive` y se le pasan al decisor). El contador se persiste en `kv` porque un reinicio no puede regalar cupo nuevo. Tampoco habla en `ENGAGED`: interrumpir mientras el señor conversa es la vía rápida a que lo silencien. **Las señales del móvil caducan** (`JARVIS_PROACTIVE_SIGNAL_FRESH_H`, 12 h): la tablet llevaba tres días sin reportar y su «batería al 1%» se veía idéntica a una lectura viva — avisar sobre eso es peor que callarse. Rutas `GET /api/jarvis/proactive` (por qué habla o calla ahora) y `POST /api/jarvis/proactive/run`. Verificado en las dos direcciones: batería al 7% recién medida → habla; estado normal → calla; lo ya dicho → calla.

### El binario del CLI puede romperse por debajo (`JARVIS_CLAUDE_BIN`)

`claudeCli.js` lanza `claude` desde el PATH, y ese binario **se auto-actualiza solo**. El 2026-08-24 saltó de 2.1.241 a **2.1.243** y la nueva versión hace **SIGSEGV en cada invocación en esta máquina**, incluido `claude --version`. Síntoma en Jarvis: TODOS los turnos devuelven el `fallbackReply` («No tengo respuesta en este momento»), `tools: null` en las trazas, cero sesiones de voz vivas, y `npm run eval:voice` se desploma — **parece una regresión del código y no lo es**.

- **Diagnóstico correcto, en este orden**: `claude --version` a pelo (sin banderas, sin config dir de Jarvis) → `coredumpctl list --since "20 min ago"` → `mtime` del directorio del paquete para ver si se auto-actualizó. Si `--version` revienta, no es Jarvis.
- **La causa aquí**: el core apunta a `free()` llamado desde `__newlocale` de libc, en la ruta `pthread_once` del arranque. Es el binario glibc de 2.1.243 contra **glibc 2.44** (CachyOS va muy adelante). Probado y descartado: `LC_ALL=C`, `C.UTF-8`, `LANG=C`, `en_US.UTF-8`, `MALLOC_ARENA_MAX=1` y `GLIBC_TUNABLES` — ninguno lo evita. La plataforma es la correcta (ELF x64 glibc, no un musl mal copiado).
- **DESENLACE (2026-08-24)**: **2.1.245 arregla el crash** — el `claude` del PATH volvió a funcionar tras una reinstalación limpia, y aguanta el arranque completo de la sesión de voz (`is_error:false` con las mismas banderas). Jarvis vuelve al binario del PATH; la línea `JARVIS_CLAUDE_BIN` queda COMENTADA en `jarvis-backend.service` y el binario musl sigue en `~/.local/bin/claude-musl` como salida de emergencia. O sea: el fallo era de 2.1.243 en concreto, no de la familia 2.1.24x.
- **Cómo se resolvió mientras 2.1.243 estuvo roto**: `sudo pacman -S musl` + `sudo ln -s /usr/lib/musl/lib/libc.so /lib/ld-musl-x86_64.so.1`, binario musl de la MISMA 2.1.243 en `~/.local/bin/claude-musl`, y `Environment=JARVIS_CLAUDE_BIN=%h/.local/bin/claude-musl` en `jarvis-backend.service`. Eval 5/5 con sesión caliente. **El `claude` del PATH sigue roto** — esto arregla Jarvis, no el uso interactivo.
- **`JARVIS_CLAUDE_BIN`** apunta a otro binario `claude` sin tocar el PATH. Sirve para quedarse en la versión nueva usando un build distinto de ELLA MISMA: existe `@anthropic-ai/claude-code-linux-x64-musl` de la misma 2.1.243, y musl no arrastra la incompatibilidad con glibc. Ojo: ese binario busca su loader en `/lib/ld-musl-x86_64.so.1`, ruta que el paquete `musl` de Arch/Cachy **no** crea (instala bajo `/usr/lib/musl/`), así que hace falta el symlink. La alternativa es fijar la versión anterior con `npm i -g @anthropic-ai/claude-code@2.1.241`.

- **El `claude` del SERVICE no es el de tu shell, y una bandera desconocida MATA la voz (2026-09-19).** Síntoma idéntico al de 2.1.243: todos los turnos devuelven el `fallbackReply`. Pero aquí `claude --version` en la terminal responde perfecto — porque el shell resuelve el CLI por **mise** (`~/.local/share/mise/installs/node/<ver>/bin/claude`, 2.1.278) mientras `jarvis-backend.service` trae `PATH=/usr/local/bin:/usr/bin` y resuelve `/usr/bin/claude`, un wrapper de 110 bytes con `DISABLE_UPDATES=1` que ejecuta `/opt/claude-code/bin/claude` — **congelado en 2.1.220 desde julio**. Comprobarlo SIEMPRE con el PATH del servicio (`tr '\0' '\n' < /proc/$(pidof -s node)/environ | grep ^PATH=`), nunca con el de la terminal.
  Lo que se rompió: el código pasaba `--autocompact`, que 2.1.220 no conoce. Commander aborta antes de arrancar, el CLI muere a los ~350 ms y el stderr lo dice literal (`error: unknown option '--autocompact'`) — **el diagnóstico estaba en journald desde el principio**. El daño colateral es peor que el visible: esa muerte cae dentro de la ventana `upMs < 5000` de `resumeBroken`, así que en cada arranque el id de sesión **rotaba y se persistía**, tirando la continuidad de la conversación. Dos síntomas, una causa.
  **El fix es un probe de capacidad, no bajar/subir de versión**: `cliSupportsFlag()` en `claudeCli.js` cachea un `claude --help` (~230 ms, pagado una vez en el warmup del boot) y solo añade la bandera si el binario la conoce. Inmuniza en las DOS direcciones — binario más viejo o más nuevo — sin forzar un upgrade sin validar ni congelar el código a una versión. Ojo al auditar banderas contra `--help`: `--system-prompt-file` **no sale en el listado** de ninguna de las dos versiones (solo se menciona dentro del texto de otra opción) y sin embargo existe; la prueba de que commander la acepta es que se quejó de `--autocompact`, que va DESPUÉS en el array de args — commander aborta en la PRIMERA desconocida.

### Superficie de herramientas de la voz (`lib/voiceTools.js`)

Un solo sitio decide qué NO puede tocar la sesión de voz, con el motivo escrito al lado de cada entrada, y un **test de deriva** que lo mantiene coherente con el prompt: la lista y el prompt viven en ficheros distintos, así que sin ese test divergen en silencio y el modelo acaba con instrucciones de usar una tool que ya no existe — e improvisa. El test además comprueba que cada nombre MCP denegado existe de verdad en `jarvis-mcp.js` (una errata deniega NADA, sin avisar).

- **Tools MCP fuera**: `remote_exec`, `remote_write_file`, `remote_read_file` (ejecución y escritura arbitrarias en OTRA máquina; a la voz le bastan `remote_machines/sysinfo/search/wake`), `code_restart` (reiniciar el backend a mitad de turno mata el propio turno) y `code_checkpoint` (mantenimiento, no conversación).

**Lo que NO se hizo y por qué**: consolidar las 7 tools de `timer` y las 7 de `chrono` en una con parámetro `action` bajaría el catálogo de 70 a ~58 y mejoraría la elección del modelo, pero cambia nombres que el prompt y el arnés usan y **no se puede validar sin CLI**; queda pendiente. El ahorro de COSTE de recortar tools es despreciable: los esquemas van en el prefijo cacheado (`cache_read`), lo caro medido son WebSearch (~18 s, $0.11) y visión (~11 s).

### Speech pipeline

1. `frontend/src/audio/localStt.ts` — `getUserMedia` at 16kHz mono, PCM via `AudioWorklet`, streams binary to `ws://backend/api/jarvis/stt/stream`.
2. `handlers/stt.js` — WS upgrade proxies to Python `stt_service.py` (`STT_URL`, default `http://localhost:8790`). Transcripts `{ text, isFinal, speakerConfidence }` flow back.
3. `handlers/speech.js` — `POST /api/jarvis/process-speech` runs intent gate. If `shouldRespond`, spawns Claude CLI.
4. TTS reply → `POST /api/jarvis/tts` → XTTS Python service.

`useLocalStt` wraps `startLocalStt()`, auto-starts/stops on `enabled` change.

### Python STT service (`backend/voice/python/stt_service.py`)

FastAPI port 8790. faster-whisper (`medium`, CPU, int8) + Silero VAD.
- `POST /transcribe` — multipart WAV, returns `{ text, language, segments[], speaker_confidence }`.
- `WS /stream` — real-time Float32 PCM. ~960 ms silence finalizes a segment.
- Speaker ID proxied through Node backend. Samples in `backend/voice/samples/speaker/`. Uses `resemblyzer`.

### Mobile QR pairing

### Gesture pipeline v2 (`frontend/src/gestures/`)

Cámara compartida (`cameraFeed.ts`, singleton, `<video>` oculto) → MediaPipe HandLandmarker **en el main thread** (`landmarker.ts`, GPU→CPU fallback) → swap handedness (`useGesturePipeline.ts`) → **engine puro** (`engine.ts`, testeable en Node) → `gestureStore`.

Engine: `features.ts` (curls world + apertura + gap) → `pose.ts` (histéresis por dedo + debounce 2 frames + histéresis sep/close del peace) → `dynamics.ts` (GrabTracker/PinchTracker/PointerTracker/TapTracker/DiscreteTracker con One-Euro (`filters.ts`), gracia de 250 ms ante dropouts, cooldown de eventos). Umbrales TODOS en `config.ts`.

**Los roles ya NO están atados a un lado fijo (2026-09-18).** La v2 daba el puntero a la mano IZQUIERDA física y el zoom a la derecha. Con UNA sola mano a la vista — el caso normal — el sistema detectaba perfectamente y aun así «no pasaba nada»: si esa mano salía como derecha solo podía hacer zoom, sin cursor, sin tap, sin arrastre del anillo y sin back. Desde el otro lado de la cámara eso es indistinguible de un pipeline ciego (medido en vivo: `R True pinch` sostenido con `L False idle`). Y la etiqueta de MediaPipe **no es estable con una sola mano**: la misma mano del usuario salió `right` en una sesión y `left` en la siguiente según la pose, así que hacer depender la función de ese lado era frágil de raíz. Ahora `engine.ts` ASIGNA el papel: la izquierda manda si está a la vista; si no, manda la que haya (`output.pointerHand` lo publica, y el monitor lo enseña). **El zoom exige la SEGUNDA mano**, a propósito: el enganche del pinch solo pide meñique/anular/corazón bajados y el pulgar cerca del índice, cosa que una mano en reposo cumple sin querer — se quedaba enganchado (el pinch es pegajoso) y `pinch.active` bloquea el arrastre del anillo en `AwakeApp`, o sea que la interfaz dejaba de responder sola. Al cambiar de mano de puntero se resetean grab/pointer/tap/discretos: sin eso el onset del grab y los filtros del puntero saltan de una mano a la otra.

Funciones (contrato de producto): MANO DE PUNTERO — puño=arrastrar/rotar (deltaX>0=derecha, deltaY>0=abajo, deltaAngle=roll), índice=cursor, **tocar el índice con el pulgar SIN deshacer el point = botón del cursor** (`tap.down/up/pressed`), V abierta soltada=click, V cerrada soltada=back (soltar = relajar dedos CON la mano visible; perder la mano cancela). MANO DE ZOOM (derecha, solo con las dos manos) — pinch=zoom RELATIVO integrado (engancha al contacto en 1.0, abrir acerca / cerrar aleja, deadband anti-temblor, pegajoso: solo suelta mano abierta / apertura >1.55 / mano perdida).

**El cursor de mano MANEJA LA INTERFAZ DE VERDAD** (`hooks/useGestureCursor.ts` + `lib/gestures/{hitTest,cursorController}.ts` + `state/cursorStore.ts`). Antes el puntero era un punto decorativo (`pointerEvents:'none'`, no pulsaba nada) y la única forma de entrar a un modo era girar el anillo con el puño y soltar, o la V; o sea el cursor señalaba y el clic iba siempre al slot enfocado, que es otra cosa. Ahora cada muestra del pipeline se convierte en `pointermove`/`pointerdown`/`pointerup`/`click` **reales** sobre el elemento que hay debajo. Lo que NO es obvio:
- **Sintetizar eventos del DOM en vez de un registro propio de objetivos** es lo que hace que funcione TODO sin tocarlo: botones del HUD, overlays y — clave — el **anillo 3D**, porque el raycast de react-three-fiber escucha esos mismos eventos sobre el canvas. Un registro propio habría duplicado el hit-test del navegador Y el de three, y habría dejado fuera lo que nadie registrara.
- **`offsetX/offsetY` se fijan a mano** en cada evento sintético: es lo que lee el `compute` por defecto de R3F para construir el rayo, y un evento construido con `new PointerEvent` no los trae.
- **Los eventos llevan la marca `__gesture`**, y el anillo la usa: con ratón, clic en un slot lateral solo lo trae al frente (dos clics para entrar, comportamiento de carrusel); **con la mano entra directo**, que es justo la fricción que sobraba. Lo que NO se hizo: seleccionar al pasar por encima (hover→select). Al girar el anillo, el slot señalado se va al frente y OTRO cae bajo el cursor quieto → se auto-selecciona → el carrusel gira solo. Un cooldown solo lo ralentiza.
- **Imantado obligatorio** (`hitTest.ts`, puro y con tests): apuntar con el dedo tiene varios píxeles de error y los botones del HUD miden ~30 px de alto. Reglas: dentro de un rect el punto NO se mueve (y gana el de menor área — el botón, no el panel); fuera, el punto se lleva DENTRO del rect más cercano, porque el evento tiene que caer sobre el elemento. Histéresis pegajosa (46 px normal, 72 px para el ya enganchado) — sin ella el cursor entre dos botones contiguos parpadea a 20 Hz y cada parpadeo reinicia el dwell y dispara enter/leave.
- **Semántica de RATÓN, no "clic al tocar"**: `pointerdown` al contacto, `pointerup`+`click` al separar, y solo si se suelta sobre el MISMO objetivo (arrastrar fuera cancela, igual que un ratón). Eso deja arrastrar gratis.
- **`:hover` de CSS NO se dispara con eventos sintéticos** (lo gobierna el navegador), así que el hover se marca con la clase `.gesture-hover`.
- **Clic por permanencia (dwell, 1.1 s) como red de seguridad**, con arco de progreso y cancelación al mover. Opt-out con `data-gesture-nodwell` en el elemento o un ancestro — puesto ya en «Dormir sistema»: un dwell accidental no puede dormir la UI.
- **Modo FINO mientras el tap está presionado** (`POINTER_FINE_GAIN`): cerrar la pinza desplaza la punta del índice, y sin esto todo arrastre empezaba con un salto y el clic acababa fuera del botón señalado.
- **Adelanto predictivo** (`POINTER_LEAD_MS`, tope `POINTER_LEAD_MAX`): el pipeline publica a ~20 Hz y One-Euro añade su retardo; el consumidor extrapola con `point.vx/vy`. Con tope, porque pasarse produce sobreimpulso al frenar, que se siente peor que el retardo.
- **`EURO_TAP` es el filtro más rápido del sistema** (minCutoff 3.0, beta 3.0): con los parámetros del pinch el contacto tardaba 3 muestras (~150 ms) en cruzar el umbral y el botón se sentía pastoso. El ruido lo para la histéresis 0.45/0.62 de apertura, que en unidades de palma es enorme frente al jitter de landmarks.
- **Calibrar el tap**: el panel «Debug gestos» muestra `tapAperture` (apertura cruda pulgar-índice de la mano izquierda) junto a los umbrales vigentes. Sin ese número, mover `TAP_ENTER/EXIT_APERTURE` es a ciegas.

Gotchas Linux/WebKitGTK (Tauri):
- **Model + WASM locales y gitignored** (`public/models/hand_landmarker.task`, `public/wasm/` — regenerar según `public/models/README.txt`).
- **La inferencia vive en el MAIN thread — un Worker es IMPOSIBLE con tasks-vision 0.10**: la librería no tiene ruta de ingesta CPU, toda imagen entra por textura WebGL (`_addBoundTextureAsImageToStream`), y los workers de WebKitGTK no tienen WebGL (probado: `GLctx.activeTexture` undefined con OffscreenCanvas; `Can't find variable: document` sin él). No re-intentar el worker.
- **Crear el landmarker tarda ~70 s en esta máquina, y rendirse antes lo EMPEORA** (medido 2026-09-18, `[gestures] GPU llegó tarde (70417 ms)`). No es el fichero: servir el `.task` de 7,8 MB tarda 12 ms — es el grafo de MediaPipe compitiendo por el main thread de WebKit con el carrusel 3D. La versión vieja abandonaba el intento a los 10 s (GPU ×2) y 12 s (CPU) para probar el siguiente, y como `createFromOptions` **no se puede cancelar**, los tres abandonados terminaban un minuto después y dejaban **un grafo VIVO con su contexto GL que nadie cerraba** (tres «Graph successfully started running» en journald, ya pasados sus timeouts). Cada timeout añadía un huérfano que competía por la GPU y hacía el siguiente intento más lento: cascada que se empeoraba sola y acababa SIEMPRE en `init CPU landmarker no respondió tras 12000 ms` — con pinta de modelo roto cuando el modelo estaba bien. Ahora `landmarker.ts` (1) espera en MINUTOS (techo 150 s por delegate), (2) **cierra el que llega tarde** (`close()` + retira su canvas), (3) solo cae a CPU si GPU **falla de verdad**, no si va lenta (lanzar las dos a la vez duplica el trabajo en el MISMO hilo: medido GPU 70 s **y** CPU 59 s en paralelo), y (4) publica progreso en el status (`construyendo grafo (GPU) · 63 s`) — un minuto de `starting` mudo es indistinguible de un cuelgue. `makeGlCanvas` ya NO borra los canvas ajenos: arrancarle el canvas a un init en vuelo le quita el nodo del que cuelga su contexto GL; solo se retiran los `live` (de un landmarker que el pipeline ya cerró).
- **`canvas` DOM EXPLÍCITO obligatorio al crear el landmarker** (`landmarker.ts`): sin él, tasks-vision usa `new OffscreenCanvas(1,1)` donde WebKitGTK tampoco da WebGL (`emscripten_webgl_create_context() returned error 0` para WebGL 2 Y 1) → el modelo carga pero `detectForVideo` muere con `GLctx.activeTexture`. Con `document.createElement('canvas')` hay WebGL2 real y hasta el delegate **GPU** funciona (renderer "WebKit WebGL"); fallback a CPU/XNNPACK si falla. Los reinicios en runtime fuerzan CPU.
- **Anti-cuelgue del main thread**: pacing adaptativo (`inferMs·PACE_FACTOR`, piso 66 ms ≈ 15 fps, techo 200 ms), frames de cámara repetidos se saltan (`nextFrame()`), `detectForVideo` lanzando → recrear el landmarker (≤3 veces) SIN tocar la cámara. v1 a 30 fps fijos saturaba el WebKitWebProcess: traps `NeedDebuggerBreak` + SIGSEGV del cliente PipeWire de WebKit (libpipewire-module-protocol-native) al morir de hambre su loop. Minimizar open/close de streams getUserMedia — ese churn dispara el mismo SIGSEGV.
- **Handedness es DIRECTA — verificada empíricamente (2026-07-05, mano por mano en el panel)**: con getUserMedia sin espejar + tasks-vision 0.10.35, label `Left` = mano IZQUIERDA física. El mapeo vive en `splitHands()` (useGesturePipeline). La nota v1 afirmaba lo contrario ("labels asumen selfie") y con ella los gestos respondían a la mano equivocada — ante cualquier duda, verificar con los badges IZQ/DER del panel debug ANTES de tocar el mapeo. Dos manos con la misma label se desempatan por x (menor x = mano derecha física).
- **Deltas y puntero salen en coords de PANTALLA** (espejo ya aplicado); consumers los usan directo. Deltas de grab normalizados por tamaño de palma en imagen (misma sensibilidad a cualquier distancia).
- **El `<video>` oculto del pipeline queda en el DOM a propósito**: `primitives.capture_photo` lo reutiliza para fotos sin re-pedir permiso. `GestureDebugView` consume el MISMO pipeline (video + `gestureStore.handsFrame`) — no abre segunda cámara ni segundo landmarker.
- **Los landmarks crudos salen por UN SOLO canal, `gestureStore.handsFrame`** (`{left, right, t}` con `HandFrame` completo: `image` + `world` + `score`). El engine los TIRA en `engine.ts:34/60` — a partir de ahí solo viven ~10 escalares de `HandFeatures` —, así que cualquier consumidor que necesite geometría de dedos (hoy solo el panel de debug) bebe de ahí y de ningún otro sitio. Se publica solo si `landmarkConsumers > 0`: se pide con `acquireLandmarks()`, que devuelve su liberador, **refcontado como `micFeed`** — dos consumidores a la vez no pueden dejarse el uno al otro sin datos al cerrarse. No hay copia: son las mismas referencias que devolvió tasks-vision, así que apagado no cuesta nada. (Antes esto era `debugFrame`, solo `image` y solo con el panel abierto.)
- **WebKitWebProcess muerto → el binario Tauri hace exit(101)** (`connect_web_process_terminated` en lib.rs) y systemd lo revive — antes quedaba ventana congelada con JS muerto. El boot espera el socket Wayland real (`ExecStartPre` en jarvis-ui.service); con `sleep 2` Tauri paniqueaba (exit 101) en cada boot.
- **Estado en `gestureStore`** (`status`/`statusDetail`/`fps`/`handsFrame`): GestureMonitor muestra backend + fps o el error real. Al apagar el pipeline el output se resetea a DEFAULT (un `active` rancio seguía rotando escenas 3D).
- **Observabilidad remota**: `GET /api/skills/gestures/status` → `{enabled, status, detail, fps}` (skill-bus verb `gesture_status`) — el health-check del pipeline sin mirar la pantalla. Además `console.*` del webview sale a journald (`enable-write-console-messages-to-stdout` en lib.rs): `journalctl --user -u jarvis-ui | grep CONSOLE`.

### Sistema de color semántico (`frontend/src/lib/theme.ts`)

El color dejó de ser decoración. Antes vivía en dos sitios que nadie mantenía a la par: unas pocas variables en `styles/design-system.css` y **106 apariciones sueltas de `#00f0ff`** dentro de los `.tsx`, más una nube de acentos improvisados (`#64ffda`, `#ffd700`, `#ff5252`, `#00e5ff`, `#38d5ff`, `#ff5f8f`) donde "verde" significaba una cosa en un panel y otra en el de al lado. Ahora `theme.ts` es la FUENTE y el CSS es su espejo.

- **Regla: el hue es significado, nunca adorno.** Siete roles: `info` (cyan, dato neutro), `deep` (azul de sombra), `attn` (ámbar, umbral superado), `voice` (magenta, voz activa), `ok` (verde, confirmado), `fail` (rojo), `idle` (pizarra, sin dato). Por eso los helpers DERIVAN el color del dato — `severityHue(value, {warn, crit, invert})` y `nodeHue(node)` — en vez de dejar que cada sitio de llamada lo elija: un 92 % de CPU se pone rojo sin que el panel tenga que acordarse.
- **`theme.ts` existe en TypeScript, y no solo en CSS, porque el 3D no lee variables CSS**: react-three-fiber necesita el hex en JS. Si el CSS fuera la única fuente, el visor y el DOM pintarían colores distintos para la misma cosa. La guardarraíl es `theme.test.ts`, que lee `design-system.css` con `fs` y compara el bloque `:root` contra `cssVars()` — misma disciplina que el test de deriva de `lib/voiceTools.js`. El bloque del CSS está entre los marcadores `>>> generado desde theme.ts <<<` y se regenera con `node -e "import('./src/lib/theme.ts').then(m=>console.log(m.cssRootBlock()))"`.
- **`--primary`/`--accent` quedan como ALIAS** (`var(--hue-info)`, `var(--hue-deep)`) porque hay ~100 usos repartidos; apuntan al rol, no a un hex.
- **La jerarquía va por LUMINANCIA, no por color**: cuatro niveles de texto (`--text` → `--text-faint`) y ni uno más — con cinco, nadie distingue el cuarto del quinto. Eso deja el color libre para lo que tiene estado de verdad.
- **`FOLDER_HUE` = un hue por carpeta de la bóveda**, y es lo que produce los cúmulos del grafo 3D: el ojo agrupa por color antes de leer una etiqueta. Una carpeta desconocida recibe un color ESTABLE por hash FNV-1a contra `FALLBACK_RAMP`, no un índice de inserción (que cambiaría al reordenar). Incluye `raiz` y `fantasmas`, que el builder del backend emite y no son carpetas reales.
- Primitivas que consumen esto: `PanelSection`, `StatRow`, `HoloMeter`, `Badge` (`frontend/src/components/`). Sustituyen los muros de estilos inline de `AwakeApp.tsx` (el panel System eran ~120 líneas con siete colores literales) y de `GestureMonitor.tsx`. **Un valor no medible es `idle`, nunca verde**: "sin dato" no es "está bien".
- Test de contraste incluido: todo rol y todo hue de carpeta contrasta ≥3:1 contra el fondo (`deg` exento: `deep` es color de sombra, nunca de primer plano). Un hue ilegible es un bug, no una elección estética.

### Grafo de conocimiento 3D (modo `vault`)

La bóveda de Obsidian, la memoria SQLite de Jarvis y las conversaciones, como UNA red navegable. Tres piezas, cada una en su capa.

- **Builder: `backend/src/lib/knowledgeGraph.js`.** `buildGraph(opts)` / `getGraph(opts)` (memoizado por `mtime` máximo de los `.md` + TTL de 30 s) / `clearGraphCache()`. Parser de frontmatter propio — **cero dependencias nuevas**, y el vault solo usa la forma simple (`key: value`, listas `[a, b]`). Resuelve `[[Target]]`, `[[Target|alias]]` y `[[Target#heading]]` contra ruta relativa, basename y `aliases`, todo **sin tildes y en minúsculas** (misma trampa que las wake phrases: `\b` solo entiende ASCII). Contra el vault real: 58 ficheros → 24 notas + 20 conversaciones + 4 facts, 59 aristas (`link:35`, `mention:23`, `fact:1`), **0 fantasmas**.
  - **Descarta el CÓDIGO antes de extraer enlaces** (bloques ``` y spans en línea). Sin esto, `CLAUDE.md`, `Wiki/CLAUDE.md` y `00-System/PROMPT-jarvis-boveda.md` producían 4 fantasmas (`ghost:asi`, `ghost:citations`…): esos ficheros ENSEÑAN la sintaxis de wikilink entre backticks. Obsidian tampoco los renderiza, y la lista de placeholders de plantilla no los cubría — enumerarlos iría siempre por detrás.
  - **Resolver va ANTES de descartar placeholders.** `[[index]]` y `[[overview]]` están en la lista de nombres de plantilla pero EXISTEN como `Wiki/index.md`/`Wiki/overview.md`; con el orden inverso se perdían dos aristas reales.
  - **Solo se colapsan las conversaciones que son un DÍA** (nombre `YYYY-MM-DD` o `type: conversacion`). `06-Conversaciones/Conversaciones.md` sigue siendo nodo `note`: es el índice al que apuntan 18 enlaces, y suprimirlo lo habría convertido en un fantasma de grado 18. Las que se caen por el tope `maxConversations` van a un set de "suprimidos" en vez de generar fantasmas — existen en disco.
  - **`MIN_TERM_LEN = 4`** para el matching de facts y menciones: por debajo ("log", "IA") el título casa por casualidad en cualquier texto y el grafo se vuelve una malla gris. Y no se emite `mention` si ya existe el wikilink explícito entre el mismo par (duplicaría el grado).
- **Layout: `frontend/src/lib/graph/forceLayout.ts`.** Force-directed 3D, **Three-free y testeable en Node** (misma disciplina que `lib/sim/` y `lib/geometry/`). Seis términos: repulsión Coulomb escalada por grado, muelles por arista con longitud de reposo POR `kind` (`link` corto = estructura real; `mention`/`fact` largos = asociación débil que no debe deformarla), gravedad de cúmulo por carpeta, gravedad al centro, amortiguación y techo de velocidad. Integración Euler semi-implícito con **`dt` FIJO** — atar el paso al frame rate haría el layout irreproducible, igual que el `FixedClock` del motor de simulación. `settle(300)` sobre 200 nodos: **68 ms**. Sobre el grafo REAL (48 nodos): 29 ms, cúmulos coherentes (6,05 intra vs 14,18 inter).
  - **Anclas de carpeta por espiral de Fibonacci, NO al azar**: dos ejecuciones tienen que colocar `03-Conocimiento` en el mismo sitio. `Math.random()` está prohibido en el módulo; el azar solo entra en las posiciones iniciales vía mulberry32 sembrado.
  - **Una sola carpeta ⇒ ancla en el ORIGEN.** Fibonacci con `count=1` daría `(R,0,0)` y arrastraría el grafo entero a un lado de la cámara — justo el caso más común (vault recién indexado).
  - **El techo se aplica a la VELOCIDAD, no al desplazamiento.** Recortar solo el paso deja energía cinética fantasma que `energy()` reportaría para siempre, y ese número es el que el renderer usa para decidir cuándo PARAR de iterar.
  - **`positions` es la MISMA referencia durante toda la vida del handle**: el renderer la lee directo en el `InstancedMesh` y reasignarla rompería el binding. Hay test de esa propiedad.
- **Vista: `frontend/src/modes/VaultGraph.tsx`.** Slot propio en el anillo principal (`vault`, que pasó de 5 a 6 slots) con holograma de preview `VaultGeo` — el ÚNICO multicolor del anillo, a propósito: anuncia el código de color antes de entrar, así el salto no cambia de idioma visual.
  - **Dos draw calls para todo el grafo**: un `InstancedMesh` de nodos y un `LineSegments` de aristas con color por vértice (gradiente de hue origen→destino, que dice la dirección sin flechas). Nada asigna memoria en `useFrame`.
  - **La simulación se CONGELA al converger** (`energy() < 0.004` o 900 frames). Un layout asentado que sigue integrando es CPU quemada sin un píxel nuevo — y con la física parada las etiquetas pueden ser DOM (`Html` de drei, tope de 14), lo que evita meter troika/SDF **y su descarga de fuente desde un CDN**, que en este equipo offline no llegaría.
  - **Filtrar ATENÚA, no oculta**: esconder los nodos que no casan rompe las aristas y el grafo deja de explicar de qué está hecho lo que sí casa. La atenuación mezcla el color hacia el fondo en vez de bajar la opacidad — con transparencia habría que ordenar 200 esferas por profundidad cada frame.
  - **Enfocar mueve la CÁMARA, no el grafo.** Anclar el nodo al centro tironearía la red entera cada vez que el señor mira otra nota.
  - Envuelto en `Model3DErrorBoundary`: un grafo que lanza dejaría la ventana EN BLANCO, no vacía (misma cicatriz que las specs 3D con dimensión inválida).
- **Rutas y voz**: `GET /api/skills/vault/graph` (en `READ_EXACT` de `toolRisk` — leer el propio vault no cambia nada) y `POST /api/skills/vault/focus` (sin listar ⇒ `write`). Tools MCP `vault_graph` y `vault_focus`; `'vault'` añadido al enum de `open_view`, a `VALID_VIEWS` y a la lista de vistas del prompt de `speech.js` — **sin lo último el modelo no elige la vista**. La primitiva `vault_focus` del renderer resuelve el nombre hablado ("la nota de física") con `resolveNodeRef`, y devuelve el nodo resuelto y no un `{ok:true}`: el verificador comprueba postcondiciones, y "enfoqué algo" sin decir QUÉ es indistinguible de haber enfocado el nodo equivocado.
- **El tamaño de un nodo codifica su número de CONEXIONES, y para que eso se LEA hacen falta dos cosas, no una** (`lib/graph/size.ts`, con tests):
  1. **Radio ∝ √grado, normalizado por el grado máximo del grafo.** La raíz es porque lo que el ojo compara es el ÁREA en pantalla: con radio ∝ grado, el hub de 26 enlaces ocuparía 676 veces el área de uno de 1. Y la normalización por `stats.maxDegree` (que el backend ya calcula) es lo que usa el rango visual completo tenga el vault 50 notas o 5000 — la versión con coeficiente fijo (`0.16 + 0.085·√grado`) metía el grueso de los nodos, grados 0 a 2, en 0.16-0.28: un rango de 1.75:1.

Medido en pantalla: nodos de grado 2 en primer plano se veían más gordos que el hub de grado 26 al fondo, y el tamaño no significaba nada. Números del cambio contra el vault real: rango por grado 4.56:1 → **7.31:1**, variación por perspectiva 2.80:1 → **1.67:1**; la señal pasa de dominar al ruido por 1.6× a dominarlo por 4.4×.

Y el resalte del nodo enfocado bajó de 1.6× a 1.25× porque hacía PARECER más conectado de lo que está justo a lo que se está mirando.
  - La leyenda **declara las dos codificaciones** (rampa de tres puntos + «tamaño = enlaces (0–N)»). Un gráfico que mete una magnitud en el tamaño y no lo dice obliga a adivinar si un nodo es grande por importante o por cercano.

  1. **`ringAngle` lo escribía el arrastre y no lo leía NADIE.** `WorldScene` derivaba el objetivo del anillo de `activeRingMode`, así que **mientras arrastrabas el carrusel no se movía un píxel** y al soltar saltaba de golpe al slot que hubiera salido. Sin feedback continuo no hay forma de apuntar. Ahora el anillo PRINCIPAL sigue `ringAngle` (slots → radianes) por un **ref vivo + suscripción imperativa** (`liveTargetRef` en `RingController`, leído dentro del `useFrame` de `RingGroup`): durante el arrastre cambia ~20 veces/s y con un selector se re-renderizarían los seis hologramas en cada muestra. Los sub-anillos siguen atados a su modo activo — sus ángulos están escritos a mano y el arrastre solo actúa en `main`.
  2. **Dos unidades en la misma variable.** `ringAngle` se mide en SLOTS (`snapToNearestSlot` hace `Math.round`, `rotateRing` escribe el índice) y el arrastre le sumaba «radianes» (`deltaYaw · RING_DRAG_SENSITIVITY`). La unidad queda documentada en `state/ringSnap.ts` y la conversión a radianes vive SOLO en el renderer.
  3. **Se integraban incrementos filtrados dos veces.** `useGestureRotation` aplicaba EMA + zona muerta + exponente 1.4 sobre el **incremento por frame**, encima del One-Euro que `GrabTracker` ya aplica. Una zona muerta sobre la DERIVADA mata los movimientos lentos enteros (a 20 Hz un gesto suave da ~0.005/frame contra un umbral de 0.015) y el exponente aplasta lo que sobrevive: había que «remar» y la correspondencia mano↔anillo se perdía al primer gesto. Ahora es `dragToRingAngle(baseAngle, deltaX, slotsPerUnit)` — **función directa** de dónde está la mano, porque `GrabTracker.deltaX` ya viene anclado al enganche y filtrado. Misma posición de mano ⇒ mismo ángulo, siempre. `useGestureRotation` y `gestureRotationHelpers` se BORRARON (no los usaba nadie más).
  - **Signo**: `deltaX > 0` (mano a la derecha) arrastra los hologramas a la derecha y trae al frente el que estaba a la izquierda, como empujar un carrusel real. En la rotación del contenedor eso es ángulo decreciente (el slot α aparece en `α − β`), de ahí el menos.
  - **`ringAngle` y `activeRingMode` describen lo mismo, y el INVARIANTE lo mantiene el store**: `setActiveRingMode` escribe también el ángulo del slot. Sin eso, tocar un holograma cambiaba el modo y el anillo —que ahora sigue al ángulo— se quedaba quieto. La excepción es `ringDragging`: durante el arrastre el resalte del slot que pasa por el frente se actualiza en vivo, y dejar que pisara el ángulo convertiría el gesto continuo en saltos de slot en slot.
- **`MAIN_RING` vive ahora SOLO en `constants.ts`.** Estaba triplicado (`jarvisStore.ts`, `WorldScene.tsx` y una cuarta copia local dentro de `AwakeApp.tsx`) más un `MAIN_RING_SLOTS = 5` escrito a mano al lado. Añadir un slot obligaba a acertar en los cuatro sitios, y fallar en el del snap hacía que soltar el arrastre seleccionara el modo EQUIVOCADO — algo que ningún tipo delata. Los ángulos de `MAIN_ANGLES` se DERIVAN de la longitud de la lista.

## Conventions and gotchas

- **Spanish UI copy.** All labels + toasts in Spanish.
- **2D→3D bridge by composite key** (`room::name`), not id. Renaming a plan in 2D orphans its 3D entities.
- **No DB in backend.** `attentionState` + `conversationMemory` are in-process globals — reset on restart.
- **STT needs Python service.** If `stt_service.py` is not running, `useLocalStt` silently fails. No auto-fallback.
- **La wake phrase se matchea en TRES runtimes y el del renderer decide primero.** `frontend/src/lib/wakePhrase.ts` (gate de `voiceMode==='wake_word'` en `AwakeApp`, vía `hasWakePhrase`/`stripWakePhrase`), `backend/src/lib/intentClassifier.js` (`hasWakePhrase`, gate de intención + unmute) y `stt_service.py` (`_WAKE_TEXT_RE`, elegibilidad del voiceprint `_wake/`). El renderer gatea ANTES de llamar al backend, así que si su regex es más estrecho el turno muere ahí y el backend nunca lo ve. **DOS TIERS**, porque los dos modos de fallo tiran en direcciones opuestas: (1) **fuerte** (`JARVIS_STRONG_RE`, en cualquier posición) = familia inventada generada por FORMA — consonante inicial `[jygh]|ch|ll` + `[ae]` + `r` + oclusiva `[vbd]` + cola cerrada (`is|ish|ist|iz|es|s|e`), o cola sola (`yaris`); cubre garbis/yardis/yardish/yardist/jervis/charvis sin enumerar, porque enumerar siempre iba por detrás; (2) **ambiguo** (`JARVIS_HEAD_RE`, SOLO en cabeza tras muletillas hola/oye/ok/no/bueno) = strings españoles reales a los que Whisper salta: `ya (lo) ves|veis|viste|oíste`, `y ahora veis`, `javier`, `jared`, `jackie` — a media frase son habla normal ("…que ya lo oíste" NO es una llamada), así que anclarlos a cabeza es MÁS preciso que el v2, que aceptaba "ya lo ves" en cualquier sitio. Todo se matchea sobre la forma **sin tildes en minúsculas** (`normalizeForWake`): `\b` solo conoce ASCII, así que sobre texto crudo "jardín" tenía frontera tras `jard` y entraba en la familia fuerte. El sufijo cerrado + `\b` es lo que mantiene fuera las palabras reales (yerba, garbo, jerbo, hervir, gervasio, yarda, jardín, jerez, jeringa, herida, gerente). Complemento en el decoder: `STT_INITIAL_PROMPT` lleva la cláusula declarativa "El asistente se llama Jarvis." para sesgar la ortografía del nombre (≥3 palabras ⇒ `_prompt_clauses` la ancla sola contra el eco). Al tocar uno, tocar los tres + sus tests (`backend/tests/intentClassifier.unit.test.js`, `frontend/src/lib/wakePhrase.test.ts`); los casos son transcripciones reales de journald. Ojo: la wake word ACÚSTICA (`wake_service.py`, openWakeWord `hey_jarvis_v0.1`) es otro camino y exige "hey jarvis" — no comparte nada con estos regex.
- **Speaker ID needs ≥1 sample.** Until enrolled, `speaker_confidence` = 0 and all voice turns are ignored. `JARVIS_OWNER_SPEAKER` env var in `jarvis-backend.service` must match the enrolled speaker name.
- **Speaker encoder is ECAPA-TDNN by default** (`SPEAKER_ENCODER=ecapa|resemblyzer`). Thresholds are encoder-scaled (ecapa ~0.55, resemblyzer ~0.70) — never copy a threshold across encoders. Changing encoder requires regenerating `owner_voiceprint.enc` via `scripts/create-voiceprint.sh` (WAV samples re-embed automatically; mismatched-dim voiceprints are skipped with a log warning). Calibrate thresholds with `scripts/calibrate-speaker-threshold.py`.
- **Speaker-id always gets RAW audio; only Whisper gets denoised audio** (`STT_DENOISE_MODE=deepfilter`). Denoise-before-embed degrades identification — don't "fix" that.
- **`_cohort/` under `samples/speaker/` is the noise-rejection anchor.** ECAPA maps pure noise to a degenerate direction that partially matches mic-channel noise in enrolled refs; the cohort gate rejects anything scoring near it. Don't delete the dir. Junk refs auto-excluded at load by a consistency filter (`ref_floor`); rejected recordings live in `<speaker>/_rejected/`.
- **Short-utterance rescue layers** (speaker_id.py + stt_service.py): duration-adaptive threshold (clips <1.5s get `SPEAKER_SHORT_THR_OFFSET` discount + stricter cohort margin), text-dependent wake voiceprint (`_wake/` dir, short clips of the owner saying only "Jarvis", `SPEAKER_WAKE_THRESHOLD`), denoised-domain retry (when the RAW match fails, the DeepFilter output whisper already consumed is re-embedded and run through the full gate stack — rescues far-field/quiet speech whose raw embedding drifts toward the noise direction; tagged `domain=denoised` so online learning stays raw-only), and trust continuity (`JARVIS_TRUST_TTL`, decaying threshold discount after a confident owner match). All layers keep the cohort gate — never bypass it. The `_wake/` clips are ALSO merged into the owner's main profile as `anchor-*.wav` copies, so short phrases score high through the standard path too.
- **Windowed voting scores windows as 1.5s clips** (duration discount + stricter cohort), and its majority-None veto only fires when some window voted a DIFFERENT speaker — uniformly weak windows are far-field speech, not mixed audio; the full-clip match (which passed all gates) wins. `SPEAKER_DEBUG=1` (default) logs which gate rejected each failed candidate (`reject thr/margin/cohort`).
- **Emitted `speakerConfidence` is CALIBRATED, not the raw cosine** (`SPEAKER_VERIFIED_CONF_FLOOR`, default 0.80): any match that survived the full gate stack (threshold + margin + cohort + rescue layers) is emitted at ≥ the floor, because short clips physically score lower cosines than the 0.60/0.65 thresholds hardcoded in speech.js/intentClassifier expect. The RAW score stays internal (logged as `raw=`) and is what feeds trust continuity and online learning — never gate learning on the calibrated value, and never "fix" a low raw score by lowering the backend thresholds.
- **STT latency architecture** (stt_service.py): speaker-id (CPU) runs CONCURRENTLY with whisper (GPU) via `_SPK_EXECUTOR` — text-dependent rescues run after decode only if the base match failed. Whisper gets the float32 array directly (no tempfile). Online learning is fire-and-forget (`_learn_async`); `learn_sample` swaps the embedding list atomically because identification reads it from another thread. A boot warmup thread pre-pays the first-decode CUDA cost (was 44s on a cold turn). Speculative decode fires at `STT_SPEC_AT=12` chunks (~0.38s of silence); per-turn log: `seg_ms (den= wh= spk=)`.
- **Endpointing is inverted-adaptive with a ~1s hard cap** (`STT_SILENCE_CHUNKS=31`): once the speculative transcript is ready, finalize at ~0.51s if it ends in `.!?` (`STT_EF_COMPLETE_CHUNKS=16`), ~0.70s if it ends in no continuation cue (`STT_EF_NEUTRAL_CHUNKS=22`), and only a trailing comma/conjunction/preposition (`_CONTINUATION_RE`, Spanish-tuned) waits the full cap. Do NOT re-invert to "require terminal punctuation to finalize early" — whisper omits Spanish punctuation so often that finished turns waited the max window. A silence tail only resets after `STT_RESUME_CHUNKS=2` consecutive speech chunks, so a lone 32ms noise blip (fan) can't restart the wait.
- **Enrollment augmentation** (`SPEAKER_AUGMENT=1` default): each on-disk reference WAV is also embedded in synthetic reverb/distance/noise variants at load and in `create-voiceprint.sh`. The encrypted voiceprint stores whatever was embedded at generation time; augmentation of `.enc`-only speakers is impossible (needs audio).
- **Linux keyring fallback.** If `secret-tool`/libsecret is unavailable (no keyring daemon), `linuxKeyring.js` falls back to `~/.config/jarvis/machine.key`. Encrypted owner voiceprint at `backend/voice/python/owner_voiceprint.enc`.
- **El micrófono del renderer es UN SOLO stream compartido** (`frontend/src/audio/micFeed.ts`, `acquireMic`/`releaseMic` con refcount + linger de 5 s). WebKitGTK captura por PipeWire y su cliente (`libpipewire-module-protocol-native`) hace SIGSEGV en el hilo `pipewire-main-l` cuando varios `getUserMedia` se abren/cierran a la vez → el WebProcess muere, `connect_web_process_terminated` hace `exit(101)` y systemd reinicia la UI. Antes había 4 streams independientes (localStt + clap + `useAudioLevel` + `WaveEqualizer`) que conmutaban en el mismo tick al cambiar `voiceMode` off↔continuo. Reglas: (1) NUNCA `getUserMedia` propio en un consumidor nuevo — pedir a `micFeed`; (2) NUNCA `stream.getTracks().forEach(t => t.stop())` sobre el stream compartido, sólo `releaseMic()`; (3) la ventana `ptt-overlay` es OTRO WebProcess con su propio singleton — sólo abre micro cuando es visible (`document.visibilityState` en `PttOverlayPage`), porque dos procesos abriendo a la vez en el boot reventaban el arranque (~1 s tras `Started`). Los cores mienten con la hora: `systemd-coredump` los reporta ~10 s tarde, mirar el campo `Timestamp` de `coredumpctl info`.
- **El aplauso SATURA el micro — NUNCA gatees por crest factor.** Medido (2026-08-04, `parec` sobre `alsa_input.pci-0000_00_1f.3` y `jarvis_aec_source`): un aplauso a distancia de escritorio llega con `peak=1.0` y 8-24 % de muestras clippeadas, así que su crest cae a 1.5-2.2 — el gate `crest > 2.5` de la v1 rechazaba justamente los aplausos MÁS fuertes (1 de 3 dobles detectados). Lo que sí separa aplauso de voz en este micro: planitud espectral (0.97-0.99 vs ≤0.86), reparto <1 kHz (2-17 % vs 59-100 %) y caída a 1/10 del pico en 80-120 ms. Además la fuente `jarvis_aec_source` (webrtc NS activo) deja el suelo de ruido en el mínimo (0.001), así que el ratio contra el suelo se dispara a ~400 para cualquier ruidito: sin el piso absoluto `absMinRms` la v1 daba **dobles falsos sólo con voz**. Umbrales todos en `CLAP_DEFAULTS` (`audio/clapEngine.ts`), tests en `clapEngine.test.ts`.
- **`jarvis-ui.service` necesita `TimeoutStartSec=90`.** Su `ExecStartPre` espera hasta 30 s por el socket Wayland pero el manager de usuario trae `DefaultTimeoutStartSec=15s` → systemd mataba el start-pre y el servicio entraba en bucle de reinicios (32 seguidos observados).
- **`nativePrimitives.js` is still Windows-first.** Camera enumeration (PnP/PowerShell) and photo capture (ffmpeg dshow) target Windows. On Linux these paths will fail silently; skill bus renderer path (`capture_photo` via MediaPipe) is the working fallback.
- **Tauri global shortcut (Super+J) only works when the Tauri binary is running**, not when using the Chromium app-mode service. For Chromium+Hyprland, wire Super+J via a Hyprland `bind` that hits the backend API.
- **3D viewer is multi-object.** `model3dStore` holds `objects: Model3DSpec[]` + `scene` opts (axes/grid); kinds: `parametric | polytope | implicit | primitive | curve | graph | vectors | plane | line | simulation`, each with per-object `position/rotation/scale/color/opacity` in MATH coordinates (z up — the viewer applies a `-π/2` X frame rotation). `show_3d` accepts `objects:[...]` or a legacy single spec; `add_3d` appends. Pure sampling math lives in `frontend/src/lib/geometry/` (`analyticMath.ts` for curves/graphs/planes/spans) — keep it Three-free so it stays Node-testable. 4D+ polytopes color edges/faces by the rotated 4th coordinate; the `_cohort`-style rule here: don't move mathjs `compile/evaluate` into render components, wrap new spec kinds in try/catch so bad LLM formulas degrade to an empty object instead of crashing the overlay.
- **`kind: 'simulation'` es el visor CON TIEMPO** — el resto de kinds son figuras estáticas; esto son sistemas físicos que evolucionan. Motor Three-free y testeable en `frontend/src/lib/sim/` (245 tests), renderers en `frontend/src/components/sim/`, transporte en `state/simStore.ts`, HUD dentro de `Model3DViewer`. Cinco `system`: **`nbody`** (orbital), **`blackhole`** (Schwarzschild), **`dynamics`** (partículas newtonianas con fuerzas y flechas vivas), **`field`** (campo vectorial + trazadores), **`ode`** (sistema dinámico cualquiera: Lorenz, péndulo doble). Rutas `/api/skills/model3d/show|add|hide` (kind nuevo) + **`/api/skills/model3d/sim`** (play/pause/toggle/reset/speed) y tool MCP `sim_control`. Lo que NO es obvio:
  - **El paso de integración es FIJO y el frame rate solo decide CUÁNTOS pasos correr** (`FixedClock`). Atar `dt` al `delta` del frame haría que la trayectoria dependiera de si el compositor soltó un frame — un sistema caótico daría un resultado distinto cada vez. El acumulador tiene tope (`maxStepsPerFrame`) y TIRA el atraso en vez de perseguirlo: sin eso, una pausa de GC encola miles de pasos y congela la UI (*spiral of death*). El multiplicador de velocidad escala el TIEMPO REAL de entrada, nunca `dt`.
  - **Gravedad va con Verlet, no con RK4, aunque RK4 sea de orden mayor.** RK4 pierde energía de forma monótona y a los pocos miles de órbitas el planeta ESPIRALA; Verlet es simpléctico y su error oscila acotado, así que la órbita sigue cerrando. Para lo NO conservativo (rozamiento, atractores, ODEs) sí se usa RK4. El HUD muestra la deriva de energía justamente para delatar un `dt` demasiado grande.
  - **El sistema solar tiene DOS modos y el bueno por defecto es el analítico.** `mode:"kepler"` propaga elipses desde los elementos J2000 de la JPL (tabla + tasas seculares en `kepler.ts`), así que acepta `startDate` y enseña **dónde están los planetas de verdad ese día**, sin deriva por larga que sea la sesión. `mode:"nbody"` integra la atracción mutua real (perturbaciones, resonancias, Lagrange) a cambio de deriva. Presets con datos reales: solar/inner/outer/earth-moon/jupiter-moons (resonancia de Laplace 1:2:4)/binary/figure8/lagrange/trappist.
  - **El preset `solar` COMPRIME los radios (`radial:'log'`) y el HUD lo dice.** De 0.39 a 30 AU en una pantalla deja el sistema interior en cuatro píxeles. La compresión conserva dirección y orden pero NO las razones, así que mentir sobre eso sería peor que no dibujarlo: por eso aparece «Radios: comprimidos (log)». Los radios de los CUERPOS van con raíz cúbica (`displayRadius`) — lineal haría invisible todo lo que no sea el Sol.
  - **El agujero negro no es arte, es la métrica**: horizonte 2M, esfera de fotones 3M, ISCO 6M, captura de luz en b = 3√3 M. Las órbitas de prueba se integran con la ecuación de Binet **incluyendo el término 3Mu²** (quitarlo da una elipse newtoniana que no precesa) y los rayos con `d²u/dφ² + u = 3Mu²`. Verificado contra la naturaleza en los tests: precesión → 6πM/p con el coeficiente correcto de 2º orden, y la deflexión casa con la serie **en el parámetro de impacto** `4M/b + (15π/4)(M/b)² + (128/3)(M/b)³` a 4 órdenes. **Ojo**: la serie que sale en muchos libros, `4M/r₀ + (15π/4 − 4)(M/r₀)²`, está en la distancia de máximo acercamiento r₀ y **no vale contra b** — usarla como referencia hace pensar que hay un bug donde no lo hay. El disco orbita a `√(M/r³)` y se colorea con cuerpo negro Shakura-Sunyaev × corrimiento gravitacional × Doppler **hacia la cámara actual**, con brillo ∝ g⁴ — por eso el lado que se acerca es el brillante y el patrón se mueve al orbitar la vista.
  - **Nada asigna memoria dentro de `useFrame`.** Buffers, matrices y colores se crean una vez y se mutan; los cuerpos son un `InstancedMesh` y las flechas un `LineSegments` + conos instanciados (dos draw calls para 1700 flechas). Las estelas son un anillo circular (`TrailBuffer`) volcado con `setDrawRange`. Es la misma disciplina que exigió el pipeline de gestos: en este WebKitGTK la basura por frame se ve como tirones.
  - **La física NO pasa por React.** Las posiciones se escriben directo en los atributos de geometría; lo único que cruza a zustand es el texto del HUD, a 4 Hz. Y `sim_control` es una ruta APARTE de `show_3d` a propósito: volver a llamar `show_3d` reconstruye la escena y **reinicia la física**, que es justo lo contrario de «pausa».
  - **`axes` de `ode` acepta EXPRESIONES, no solo nombres de variable** — por eso el péndulo doble se integra en (θ,ω) y se dibuja como un péndulo de verdad en el espacio real, con las varillas rígidas por construcción.
### Realismo del simulador (2026-09-19)

Las simulaciones pasaron de esferas de color plano bajo luz cyan a cuerpos texturizados con física por encima de Newton. Dos capas nuevas — apariencia (`lib/sim/appearance.ts`, `planets.ts`, `scene.ts`) y correcciones físicas (dentro de `nbody.ts` y `dynamics.ts`) — más ~60 tests. Interruptor maestro `realistic` en `SimCommon` (default **true**); `realistic:false` recupera el modo esquemático anterior intacto.

**Apariencia.** Texturas en `frontend/public/textures/` (**gitignoreadas**, ~7,3 MB, CC BY 4.0 de solarsystemscope.com; se regeneran con `./scripts/fetch-sim-textures.sh`). `appearance.ts` es la tabla: oblicuidad, periodo de rotación, anillos, nubes y mapa nocturno por cuerpo; `presets.ts` la REFERENCIA con `appearanceFor(nombre)` en vez de copiar números. Lo que NO es obvio:

- **Los cuerpos texturizados salen del `InstancedMesh`, los demás NO.** Cada textura es un material distinto, o sea una draw call por cuerpo. En el sistema solar son 10 mallas — nada; aplicado a las 1000 partículas de un `dynamics` sería el fin del frame rate. Por eso decide `needsOwnMesh()` **por cuerpo**, y el que tiene malla propia se esconde del instanced poniendo su escala a **0** en lugar de sacarlo del buffer: los índices los comparte con el motor y con las estelas.
- **`SphereGeometry` pone sus polos en ±Y y aquí se trabaja en z arriba.** Sin rotar la geometría π/2 en X, la textura sale tumbada y el planeta gira sobre un eje que le atraviesa el ecuador. Se rota la geometría UNA vez y se comparte.
- **La rotación retrógrada está dicha DOS veces en las tablas de la NASA** — periodo negativo Y oblicuidad > 90° (Venus 177.36°, Urano 97.77°) —, así que aplicar las dos se cancela y Venus acabaría girando al derecho. `spinSign()` descuenta una contra la otra.
- **Los periodos se ALARGAN todos por el mismo factor** (`spinSlowdown`): a 20 días por segundo del preset `solar` la Tierra daría 20 vueltas por segundo, que no es rotación sino aliasing. Factor único ⇒ las razones se conservan (Venus sigue tardando 243 veces lo que la Tierra). Misma concesión declarada que los radios exagerados.
- **La UV de `RingGeometry` recorre un CUADRADO**, y la textura de anillo es un perfil radial de una dimensión: sin reescribir el atributo a `u = (r−interior)/(exterior−interior)`, el hueco de Cassini no cae donde debe. Los anillos cuelgan del nodo INCLINADO, no del que gira: son partículas en órbita propia.
- **`emissiveMap` da el terminador día/noche gratis**: se suma DESPUÉS de la iluminación, así que las luces de ciudad aparecen justo donde no llega el Sol, sin shader propio.
- **La luz de la estrella va DENTRO del grupo del cuerpo**, no clavada en el origen: en un binario las dos estrellas se mueven y una luz fija iluminaría desde donde no hay nada. Y lleva **`decay = 0` a propósito**: el preset `solar` comprime los radios en logaritmo, así que una caída con el cuadrado sobre distancias FALSAS no da el brillo real, da un número sin significado — dejaba Neptuno negro. Iluminación uniforme desde la dirección de la estrella es lo que hace un planetario.
- **Un sistema SIN estrella propia no puede iluminarse desde el origen.** `earth-moon` y `jupiter-moons` no incluyen al Sol, y ahí el origen es el BARICENTRO, o sea un punto dentro del cuerpo principal: la Tierra salía alumbrada desde su propio centro y la sombra que produce un eclipse no existía. El modelo correcto es una luz **direccional** — a 1 UA los rayos del Sol son paralelos sobre un sistema de 384 000 km — y de propina su sombra es un mapa plano en vez de cúbico, seis veces más barata. Su cámara de sombra es ORTOGRÁFICA y sin encuadrar se recorta a 10 unidades, así que la umbra desaparecía justo cuando los cuerpos se separan; se dimensiona con la extensión de la escena.
- **`castShadow` no hace NADA con el mapa de sombras del renderer apagado**, y el visor lo trae apagado porque las figuras abstractas no lo usan. `ShadowMapToggle` lo enciende y **restaura el valor anterior** al desmontar. Tope de 12 cuerpos: una `pointLight` con sombras cuesta un mapa CÚBICO (seis renders por frame), y Tierra-Luna —donde la sombra SIGNIFICA algo, el eclipse— va sobrado mientras el sistema solar completo es un tirón permanente.
- **Escena** (`scene.ts` + `Model3DViewer`): el ambiente **cyan** de 0.45 teñía todo (Marte salía malva). En modo realista se sustituye por ambiente blanco tenue + fondo equirectangular de la Vía Láctea como `scene.background` (no una esfera: una esfera invertida entra en el raycast y se traga los clics) + `ACESFilmicToneMapping`, **todo restaurado al desmontar**. El modo holográfico queda bit a bit igual.

**Física.** `nbody.ts` gana tres términos, todos funciones puras exportadas y contrastadas contra la naturaleza, no contra sí mismas:

- **1PN relativista** (`relativisticAccel`): el término de Schwarzschild `(GM/c²r³)·[(4GM/r − v²)r⃗ + 4(r⃗·v⃗)v⃗]`. Mercurio precesa **43″/siglo** — el test comprueba la forma cerrada `6πGM/(c²a(1−e²))` contra el valor observado, y además integra la órbita y mide.
- **Achatamiento J2** (`oblatenessAccel`) con los datos reales de `planets.ts`. El test lo valida contra la fórmula secular de regresión nodal `dΩ/dt = −(3/2)n·J2(R/p)²cos i`.
- **Colisiones con fusión**: conservan masa y momento; el test exige que la energía nunca SUBA (el fallo clásico de un solver mal escrito).

Lo que NO es obvio, y costó encontrarlo:

- **Las correcciones se encienden solo en UNIDADES SOLARES REALES** (`G ≈ G_AU`). La c del término 1PN vale 173.1446 **AU/día**, número que solo significa algo si las longitudes son AU y los tiempos días. `figure8` es una coreografía en unidades arbitrarias (G = 1) y aplicarle relatividad no es "más realista": **rompía la cerrazón de la órbita en ocho**, que es una solución EXACTA de la gravedad newtoniana — el test de ese preset fue quien lo delató. Ojo: `binary` y `lagrange` PARECEN figuras de juguete y no lo son (usan G_AU con la masa y el semieje reales de Júpiter), así que sí las llevan. Hay test de regresión de las dos direcciones.
- **El 1PN depende de la VELOCIDAD y `VelocityVerlet` solo entrega posiciones** a su campo de aceleración — es justo lo que lo hace simpléctico. Se lee la velocidad viva del motor, medio paso desfasada. Es deliberado: la corrección entera vale O(v²/c²) ≈ 1e-8 del término newtoniano, así que ese desfase queda muy por debajo del error de truncamiento del paso. Lo que NO sería inofensivo es cambiar a un integrador dependiente de la velocidad: la órbita empezaría a espiralar, que es lo que este motor evita.
- **El ruido de truncamiento del Verlet es MAYOR que la señal relativista**: a dt = 0.02 d mueve el perihelio newtoniano ~1.5e-4 rad, siete veces los 2e-5 rad que la relatividad aporta en 40 órbitas. Por eso la medida se hace **restando dos corridas** (idéntico error en ambas, se cancela) y casa al 2.5%. Medir la corrida relativista contra cero mezclaría las dos cosas.
- **Un cuerpo fusionado no se BORRA, se marca muerto** (`alive: Uint8Array`) y se aparca dentro del absorbente: el renderer tiene los buffers dimensionados al número de cuerpos del arranque. Y como queda a r = 0 del absorbente, **sin la máscara el potencial da 0/0 = NaN** y la deriva de energía del HUD queda ilegible el resto de la sesión. `gravityAccel`, `totalEnergy`, `relativisticAccel` y `oblatenessAccel` aceptan todas la máscara.
- **Las colisiones usan el radio FÍSICO, nunca el de dibujo.** Los cuerpos se pintan exagerados a propósito; con el de dibujo la Tierra chocaría con Marte a un cuarto de UA. La Tierra mide 4.26e-5 AU frente al 0.1 con que se dibuja — mil veces menos. Sin `collisionRadii` no hay colisiones, y por eso están APAGADAS por defecto: en el sistema solar real nada choca, y encenderlas de serie haría que un `softening` mal puesto se comiera planetas.
- **J2 de Júpiter es solo 13.6× el de la Tierra**, no 200 (el primer comentario decía eso y era falso). Lo que hace que su achatamiento mande es que el término va con **J2·R²** y su radio es 11× mayor: el producto sale ~1600 veces el terrestre.
- **Las líneas de campo se colorean por |F|, y eso costó cero**: son estáticas (una foto del campo), así que el color se calcula al construir la escena y no por frame. Una línea de color plano dice por dónde va el campo pero no cuánto vale, y en un dipolo eso son dos órdenes de magnitud entre el centro y el borde. Se normalizan contra el máximo GLOBAL, no contra el de cada línea — si no, la más débil se pintaría igual de intensa que la más fuerte. `vortex`, `source` y `saddle` no traían líneas en absoluto: solo flechas y trazadores. La rampa de color vive ahora en `fieldRamp()`, compartida con las flechas (estaba escrita a mano dentro de su bucle, y con dos consumidores era cuestión de tiempo que dejaran de decir lo mismo).
- **`dynamics` tenía un preset `collision` donde nada colisionaba** — solo había rebote contra suelo y caja, las partículas se atravesaban. Ahora `resolveCollisions()` (impulso normal, contacto por proyección) y `friction` (Coulomb, **acotado por μ·|vn|**: restar μ·|vn| a secas dispararía hacia atrás a una partícula casi parada, energía de la nada). Un par que YA se separa se ignora, o el dúo entra en un zumbido contra el paso del integrador.

**Lente gravitacional del agujero negro** (`schwarzschild.ts` + `BlackHoleLens.tsx`). Antes los rayos se dibujaban curvados —se VEÍA que la luz se dobla— pero el fondo detrás del agujero no se deformaba, que es lo que produce el anillo de Einstein y la imagen secundaria. Ahora el cielo se deflecta con la misma geodésica nula que ya estaba verificada por tests. Lo que NO es obvio:

- **La LUT se indexa en `ln(b/b_crit − 1)`, no en b.** En deflexión fuerte δ ≈ −ln ε + const, así que en ese eje la función es casi una recta y la interpolación lineal del shader es casi exacta (error medido 2.6e-5 rad). Muestrear en b gastaría la tabla en la zona plana y dejaría el anillo de fotones con cuatro puntos.
- **Es un `mesh` de pantalla completa dentro del Canvas que ya existe**: sin render target, sin composer, sin segundo contexto. 17.7 ms de CPU una vez al montar (δ(b) es propiedad de la métrica, no depende de la cámara) y un pase de pantalla por frame.
- **`sin ψ` vale lo mismo a los dos lados de 90°**, así que sin condicionar la captura a que el rayo apunte HACIA el agujero, el punto del cielo exactamente OPUESTO salía negro.
- **El DISCO no se deflecta, solo el fondo** — no hay halo tipo Interstellar. Hacerlo pide ray-marching por píxel (hunde esta iGPU) o un render target con segunda pasada. Es la mejora natural siguiente.
- **La lente pinta el fondo de TODA la pantalla**, no un disco alrededor del agujero: es lo único que hace que el cielo lejano case sin costura con el doblado. Consecuencia: un `blackhole` junto a figuras abstractas cambia el fondo a la Vía Láctea. Se apaga con `lensing: false`.

**El spec lo escribe un MODELO, así que llega con los tipos cambiados** (2026-09-19, y costó tres reconstrucciones encontrarlo):

- **`rays: 9` llegaba como la CADENA `"9"`.** `typeof spec.rays === 'number'` fallaba, la cadena atravesaba intacta y el renderer llamaba `.map` sobre ella. La excepción la recogía `Model3DErrorBoundary` — que hizo su trabajo: app viva, figura descartada — y en pantalla quedaba un **agujero negro completamente VACÍO** cuya única explicación era una línea en journald. Es el peor modo de fallo posible: silencioso y con pinta de "no se implementó".
- **`disk: false` llegaba como `"false"`**, y `spec.disk === false` en estricto da falso: el disco seguía dibujándose después de pedir que se apagara. Mismo caso en `markers`, `relativistic` y `lensing`.
- De ahí los tres coercionadores de `BlackHoleView.tsx` (`num`, `bool`, `asArray`, este último con `JSON.parse` para un array serializado) y `blackHoleSpec.test.ts`, que verifica que **`buildBlackHole` no devuelve NUNCA algo que el renderer no sepa dibujar**, entre lo que entre. Ningún campo puede salir NaN: un NaN no lanza, simplemente dibuja la nada.
- **Un array VACÍO significa "ninguno", no "ponme los de siempre".** Sustituirlo por el default hacía imposible apagar los rayos, que es justo lo que hay que hacer para mirar la lente sola.
- **`args={[undefined, undefined, Math.max(1, n)]}` en un `InstancedMesh` con n = 0 reserva una instancia cuya matriz se queda en IDENTIDAD**: una esfera de radio 1 plantada en el origen. Con cero órbitas eso era una **bola BLANCA justo encima del agujero negro**, tapándolo entero. No se había visto nunca porque hasta ahora era imposible pedir cero órbitas. Corregido en los dos renderers.
